# 03 — PolyMechanism Studio 项目执行计划

> **PolyMechanism: A Physics-Grounded Scientific Agent for Mechanistic Discovery in Polymer Processing**
> 面向高分子加工物理机理发现的科学智能体工作台。本计划基于对 `dsh-desktop` 全部源码的阅读（见 01 文档）与两份前期调研资料（Harness 领域插件范式调研 / 桌面产品架构方案）综合制定。

---

## 0. 定位与总原则

**一句话**：以 DSH 为 Agent 引擎、以本 fork 桌面壳为载体，构建"多专家 Agent + 科研业务引擎 + Python 科学计算"三位一体的高分子科研工作台，科研创新点落在**机理图谱形式化 + 竞争假设推理 + 实验证据闭环**。

四条不可动摇的原则：

1. **复用优先**：Agent Loop、上下文管理、会话、工具调度、MCP、插件生命周期全部复用 DSH/Cordis；自研代码只写"高分子领域层"。
2. **科研业务与 Harness 解耦**：Evidence / Hypothesis / MechanismGraph / PhysicsModel 等核心科学资产是纯 TypeScript 领域包（`packages/domain`），不 import 任何 `@deepseek-ai/*` 内部类型——将来换 Harness，科学资产仍可用。
3. **证据先于结论**：任何"机理结论"必须挂接可追溯证据（实验数据、文献 DOI、模型拟合指标）；Agent 可以提出解释，但不能自行把解释变成已验证事实（借鉴 GeoResearch 的推理/业务分离思想）。
4. **一个版本一台柱子**：严格按阶段推进，每阶段有可运行的验收物，不跨阶段堆功能。

## 2. 多专家 Agent 设计

### 2.1 Agent = Runtime + Persona + Tools + Skills + Knowledge + Policy

六个专家共享同一 DSH Runtime 与 Agent Loop，差异只在：Persona（身份与纪律）、Tools（工具白名单）、Skills（方法论文档）、Knowledge（理论库挂载）、Policy（权限与审查门槛）。**不为任何专家单独开发 Agent Loop。**

| Preset | 角色 | 关键工具（白名单） | 禁止事项 |
| --- | --- | --- | --- |
| `polymer-scientist` | 任务总控/首席，分解课题、委派、汇总 | 全部只读 + 委派(subagent) + 项目管理工具 | 不得直接改 Evidence 状态；不得下"已验证"结论 |
| `polymer-physicist` | 高分子物理理论专家：机理候选生成、理论解释 | 机理图谱查询/写入候选边、文献检索、模型调用 | 不得操作实验设备数据采集 |
| `polymer-characterization` | 表征专家：SAXS/WAXS/FTIR/光学数据解析 | Science MCP 表征工具、数据导入、质量检查 | 不得修改理论模型参数库 |
| `polymer-modeler` | 建模专家：物理模型拟合、数学推导、判别实验设计 | 模型注册表 CRUD（草稿态）、拟合/仿真工具 | 不得将拟合结果直接登记为证据 |
| `polymer-literature` | 文献专家：检索、精读、结构化摘录入库 | 文献工具、DOI 验证、图谱"理论来源"写入 | 只写"文献证据"，不写实验结论 |
| `polymer-reviewer` | **独立审查者**：证伪、核查证据-结论链 | 证据账本只读 + 审查工具 + Objection 登记 | 与提出者天然分离；产出写 Objection Ledger |

### 2.2 能力矩阵（权限最终由插件与服务端规则强制，非仅 Prompt 约定）

| 能力 | Scientist | Physicist | Charact. | Modeler | Literature | Reviewer |
| :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 高分子理论 | ✓ | ✓ | ○ | ✓ | ○ | ✓ |
| 文献检索 | ○ | ✓ | — | ○ | ✓ | ✓ |
| SAXS/WAXS/FTIR | — | — | ✓ | ○ | — | ○ |
| 数学建模 | ○ | ✓ | — | ✓ | — | ✓ |
| 科学仿真 | — | ○ | — | ✓ | — | — |
| 证据核验 | — | — | ○ | — | — | ✓ |
| 假设生成 | ✓ | ✓ | ○ | ✓ | — | — |
| 独立证伪 | — | — | — | — | — | ✓ |

✓=完整 ○=只读/受限 —=无

### 2.3 协作拓扑

```
                    ┌─────────────────┐
   用户/科研课题 ──▶ │ polymer-scientist │─── 委派 ──▶ physicist / modeler /
                    └────────┬────────┘            characterization / literature
                             │ 登记假设/证据/结论（经业务服务，非自由写）
                             ▼
             Evidence Ledger ⇄ Hypothesis Manager ⇄ Mechanism Graph
                             ▲
                    ┌────────┴────────┐
                    │ polymer-reviewer │ ◀── 高风险节点强制触发（Scientific Gate）
                    └─────────────────┘
```

- **委派**用 DSH 原生 subagent 机制；跨会话长任务用原生 workflow。
- **Scientific Gate**（服务端规则，见 §3.6）：假设升级为"机理结论"、证据跨级引用、结论写入报告——三类操作强制先过 reviewer。
- **实现方式**：每个专家一个 preset patch（`presets/*.patch.yml`），组合官方 Standard Preset + persona + 工具白名单 + skills；具体键名以锁定版本上游 `dsh-agent-preset` 的声明式配置为准（仓库内 vendored runtime 可直接对照源码，**不要照搬前期资料中旧版 `preset.yml` 写法**）。

## 3. 内置科研引擎（Cordis Host 插件 + 领域包）

全部遵循上游三角色模式：**Service Definition（契约，`packages/domain/contracts`）→ Service Provider（插件实现）→ Consumer（工具注册 + UI）**。

### 3.1 Research Manager（科研项目管理）

- 实体：`ResearchProject`（课题、状态、成员 Agent、里程碑）、`Epic/Issue`（借鉴 Research Epic Manager 的长周期任务管理）。
- 持久化：项目目录内 JSON/SQLite + 哈希审计日志；**项目状态 ≠ 会话历史**——一周后上传新 WAXS 数据，Agent 能从项目状态续跑而非重读全部背景。
- 工具：`project_create` / `project_status` / `epic_add` / `issue_update`。

### 3.2 Evidence Ledger（证据账本）

- **Append-only 事件流**：`Observation | LiteratureRecord | FitResult | SimulationResult | ReviewVerdict`，每条含来源、哈希、时间、登记者。
- 结论必须引用 `evidenceIds[]`；引用不存在的证据 → 服务层直接拒绝（这是程序约束，不是提示词）。
- 工具：`evidence_record` / `evidence_query` / `evidence_link`。

### 3.3 Hypothesis Manager（假设状态机）

```
proposed → conditional(需指定判别实验) → under_test → supported / refuted → archived
                        ↑ 新证据到达时回流 under_test（不推倒重来）
```

- 每个假设绑定：竞争假设集合、判别实验设计、预期观测量、当前证据引用。
- 工具：`hypothesis_propose` / `hypothesis_transition`（状态迁移合法性由服务端校验）/ `hypothesis_list`。

### 3.4 Mechanism Graph（机理图谱）★核心创新之一

- 节点：物理量/过程（如"拉伸比 λ"、"Hermans 取向因子 f"、"弛豫时间 τ"）；边：候选物理关系，属性含 `theorySource(DOI) / direction / applicabilityConditions / equation / supportingEvidence[] / conflictingEvidence[] / openQuestions[]`。
- 与 RAG 的区别：存**关系**而非文本片段；Agent 对实验现象做图查询（如"哪些路径可解释 f 随时间衰减且受温度调制"），得到候选机理路径而非相似段落。
- 种子内容：`knowledge/mechanism/` 下人工整理的 PVA 体系候选关系（标注"未验证"）。
- 存储：SQLite（关系表）+ GraphML 导出；UI 用 React Flow（见 02 文档级别 3）。

### 3.5 Model Registry（物理模型注册表）★核心创新之二

每个模型 = 可执行科学资产：`model.yaml`（参数/约束/适用边界）+ Python 实现 + 参考数据 + 测试。

首批目录（对应 PVA 光学膜课题）：

| 模型 | 用途 |
| --- | --- |
| Rouse / Reptation | 非缠结/缠结链动力学 |
| Maxwell / KWW | 黏弹性与分布型松弛 |
| WLF | 时间-温度等效 |
| Avrami（标注适用条件） | 结晶动力学 |
| Flory–Huggins | 溶液热力学 |
| Hermans 取向因子 | 取向表征 |
| 应力光学规则（SOR）+ 两相双折射模型 | 晶区/非晶区光学贡献分解 |

- 状态：`draft → validated(过测试+参考数据) → deprecated`；只有 `validated` 模型可被判别实验引用。
- 工具：`model_search` / `model_describe` / `model_fit`（转 Science MCP 执行）。

### 3.6 Scientific Gate（审查门）

服务端规则引擎：三类高风险操作（假设→结论升级、结论进报告、跨项目证据引用）触发 reviewer 子代理独立审查；审查产出写 `ReviewVerdict`（含 Objection Ledger 的反对意见与未决问题）；**人类保留最终裁决**（UI 审批卡片）。借鉴 dsh-research-plugins 的权限分离设计，但以本仓库原生插件机制实现。

### 3.7 Report Generator

`WritingPacket`：从证据账本拉取被引用证据全文 + 图表 + 模型参数 + 审查记录，生成科研报告/论文素材包（Markdown + 数据附件），每段声明证据 ID。工具：`report_draft` / `report_verify`（核对引用完整性）。

## 4. Python Science Engine（MCP）

**原则：普通科学计算直接走 MCP，不为了架构统一而重复封装成 Cordis 工具**（见前期资料 §6 的分流表）。`science/` 包用 uv 管理，`mcp_server.py` 暴露 FastMCP 服务，DSH 原生 MCP client 接入（范式同 dsh-mol 的 RDKit→Polymer 替换）。

```
science/polymechanism/
├── characterization/   # SAXS/WAXS( pyFAI, SasView models )、FTIR 峰解析、
│                       # 双折射/Hermans 因子计算、数据质量门检
├── physics/            # Model Registry 的可执行实现（与 model.yaml 一一对应）
├── modeling/           # 拟合( lmfit )、参数辨识、不确定性、模型判别统计
├── simulation/         # 粗粒化 MD 接口（LAMMPS，参考 ToPolyAgent）
├── experiment_design/  # 判别实验设计（哪个实验能最大程度区分竞争假设）
└── mcp_server.py
```

首批 MCP 工具：`saxs_reduce` / `waxs_crystallinity` / `ftir_peak_fit` / `fit_relaxation(maxwell|kww)` / `hermans_factor` / `simulaterouse` / `design_discrimination_experiment`。
数据格式：实验原始数据 HDF5/Parquet；结果回写经 `evidence_record` 登记为 `FitResult/SimulationResult`（哈希存证）。

### Phase 1 — Skill-first MVP（第 1–2 周）

**目标：不写任何插件，先验证科研闭环的方法论价值。**

- 建 `PolyMechanism-MVP` 科研工作区：`.dsh/skills`（4 个核心 Skill）+ `knowledge/` + `scripts/` + `experiments/`。
- 接入 Python MCP（先 4 个工具：`fit_relaxation` / `hermans_factor` / `waxs_crystallinity` / `ftir_peak_fit`）。
- 用真实 PVA 数据跑通：读数据 → 拟合 → 生成带证据引用的机理解释报告。
- **验收**：一份端到端 PVA 取向松弛案例报告；专家（用户）评审"解释是否有物理含量"。

### Phase 2 — Plugin-first（第 3–6 周）

**目标：把验证过的流程固化成插件与专家 Presets。**

- `packages/domain` 契约定型 → `plugins/*` 六个 Host 插件 → `polymechanism-tools` 工具注册 → 六个专家 preset patch。
- UI：Mechanism 图谱 / Hypothesis 看板 / 项目持久化恢复（02 文档级别 3）。
- **验收清单**：新建项目→导入数据→登记证据→提假设→委派建模→图谱更新→审查通过→导出报告，全流程无人工改文件；重启后项目状态完整恢复。

### Phase 3 — Discovery-first（第 7–12 周及后续）

**目标：实现竞争性机理生成、模型判别、真实实验验证与科学审查——论文核心实验期。**

- Scientific Gate + Objection Ledger 全量上线；判别实验设计器（`design_discrimination_experiment`）。
- 完成第一轮真实 PVA 科研案例（竞争假设 ≥2，判别实验 ≥1，独立证伪 ≥1 轮）。
- 对比实验：单 Agent vs 多专家系统在机理判别任务上的表现（论文素材）。
- **验收**：系统产出的机理结论被领域专家（导师/合作者）评审为"物理上可辩护"；证据链无断链。

### Phase 4 — 产品化（持续）

- 安装包（exe/dmg/deb/AppImage）分发、Science 环境首启安装、更新服务上线、文档站。
- Beta 包与上游新版本跟进策略（镜像规则恢复执行）。

| 更新服务缺位 | 端点已切占位域名，更新静默失败；Phase 0.5 自建或显式禁用 |

| 科学严谨性 | Agent 永远不拥有"事实写入权"——Evidence/Hypothesis 状态迁移只在服务端发生且可审计；结论必须过 Gate + 人工裁决 |
| Beta/Stable 分叉维护成本 | fork 期只保 Stable；恢复镜像规则前不升上游版本 |

## 9. 与现有研究的差异声明（论文定位）

截至 2026-11：基于 Harness 做领域科研 Agent（GeoResearch、Research Epic Manager 等）与高分子科学 Agent（STCA、ToPolyAgent、SasAgent、Polymer-Agent）均已存在。**"基于 Harness 的科研 Agent"与"高分子 Agent"本身不再构成创新点**。PolyMechanism 的原创贡献锁定为：①高分子加工机理的形式化表达（Mechanism Graph）；②竞争假设的主动判别与证伪闭环（Scientific Gate + 判别实验设计）；③多模态实验证据与物理模型的可追溯集成。对比表见前期调研资料 §11，论文方法章节将以此三点为主轴。
